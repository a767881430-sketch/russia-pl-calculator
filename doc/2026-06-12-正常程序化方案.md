# 俄罗斯损益计算器正常程序化方案

## 结论

用户希望它像 `D:\星哈酷ERP\XingHaKu_ERP` 一样，是一个正常程序，而不是一个单独静态网页再外接数据库。

最推荐方案：俄罗斯损益计算器单独做成一个“客户版正常程序”，不要并入 XingHaKu ERP。

原因：
- ERP 已经承载很多内部功能，不适合给还没有合作的客户、老板、供应商直接使用。
- 计算器面向外部决策沟通，需要入口更简单、界面更干净、权限更克制。
- 独立系统可以只保留项目测算、公开查看、分享、客户只读，不暴露 ERP 的订单、库存、财务同步、店铺 API 等内部模块。
- 后端形态仍参考 ERP：FastAPI、数据库迁移、登录权限、一键启动、阿里云部署。

## 目标形态

用户看到的是一个独立入口：

```text
俄罗斯项目损益测算系统
```

登录后可以：
- 新建项目；
- 编辑项目；
- 保存到数据库；
- 发布公开只读链接；
- 复制临时快照链接；
- 管理历史项目；
- 老板、供应商、运营新人按不同视角查看。

老板或供应商打开公开链接时，可以免登录只读查看。

## 推荐技术形态

### 本地开发

参考 ERP 的工程形态，但放在当前计算器项目里：

```text
backend_api/                FastAPI 后端
frontend/ 或保留当前 src/     React/Vite 前端
alembic/                    数据库迁移
.env.example                环境变量模板
一键启动损益计算器.bat
```

### 阿里云正式部署

推荐：

```text
阿里云 ECS        跑 FastAPI + Next.js/Nginx
阿里云 RDS        存项目数据
Nginx             统一域名、HTTPS、前后端转发
```

可选：

```text
OSS/CDN           只用于静态资源加速，不作为数据库
```

## 后端模块设计

在当前计算器项目中新建后端：

```text
backend_api/
backend_api/main.py
backend_api/models.py
backend_api/database.py
backend_api/auth.py
backend_api/api/projects.py
backend_api/api/public.py
```

主要接口：

```text
GET    /api/projects
POST   /api/projects
GET    /api/projects/{project_id}
PUT    /api/projects/{project_id}
POST   /api/projects/{project_id}/publish
POST   /api/projects/{project_id}/share-links
GET    /api/public/{slug}
GET    /api/share/{token}
POST   /api/auth/login
POST   /api/auth/logout
GET    /api/auth/me
```

权限：
- `admin`：管理全部项目、发布公开链接、创建账号；
- `editor`：可新建、编辑、保存、发布自己负责的项目；
- `reader`：登录后只读内部项目；
- 公开链接：只读，不需要登录，适合给客户老板、供应商、新人看。

## 数据库表设计

当前计算器独立数据库新增：

```text
investment_projects
investment_project_versions
investment_project_share_links
```

字段保留当前项目 JSON 结构：

```text
params
products
scheduleStore
priceScheduleStore
restockStore
withdrawalStore
projection
projectMeta
projectName
```

这样不会重写现有公式。

## 前端模块设计

在当前计算器前端保留现有页面体验，调整为调用独立后端：

```text
/login
/app/projects
/app/projects/:id
/p/:slug
/share/:token
```

对外只暴露：

```text
公开项目页
临时分享页
必要时的客户只读登录
```

当前 Vite 计算器里的计算逻辑优先复用：

```text
src/lib/calcEngine.js
src/lib/platformPricing.js
src/lib/platformTariffs.js
src/lib/projectData.js
```

## 实施顺序

1. 先做后端表和接口，不动公式。
2. 把当前项目 JSON 保存到 ERP 数据库。
3. 前端先接入项目库、保存、读取、发布。
4. 把 Supabase 调用替换成独立后端 API 调用。
5. 做本地一键启动脚本。
6. 做阿里云 ECS + RDS 部署说明和一键部署脚本。

## 不推荐的方式

不推荐让浏览器直接写 OSS 文件。

原因：
- 需要暴露阿里云写入密钥，安全风险高；
- 多人同时编辑容易覆盖；
- 权限、版本、公开链接都不好管理；
- 以后很难变成正式系统。

## 当前判断

如果目标是“像正常程序一样长期给客户老板使用”，不要继续把它当 GitHub Pages/OSS 静态计算器维护，也不要并入内部 ERP。

下一阶段应开始做独立全栈程序化改造：后端先行，前端渐进接入，公式保持兼容。
